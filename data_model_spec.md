# Data Model Specification

**Project:** Multimodal AI Healthcare Decision-Support System
**File:** `data_model_spec.md`
**Status:** Initial Draft

## 1. Purpose and Ownership

This specification defines the logical data model for the initial release: entities, key fields, relationships, constraints, and lifecycle states. It implements the data domains in `backend_spec.md` Section 5.2.

- Physical details (exact column types, indexes beyond those listed) are decided in migrations and must stay consistent with this document.
- Entities are built incrementally. Section 9 records which entities exist in the database.
- API shapes are owned by `api_contract_spec.md`; database models are never exposed directly (`backend_spec.md` Section 3.1).

## 2. Conventions

| Rule | Detail |
|---|---|
| Primary keys | UUID (`id`), generated by the application. |
| Ownership | Every user-owned table has `user_id` (FK → `users.id`, not null). All queries filter by it (`backend_spec.md` Section 8.2). |
| Timestamps | `created_at`, `updated_at` as `timestamptz` in UTC. Clinical dates keep their own precision (Section 2.1). |
| Enumerations | Stored as text with a CHECK constraint listing allowed values. |
| Provenance | Clinical records carry `origin` (`user_entered`, `document_extracted`, `suggestion_accepted`), `source_document_id`, and `source_location` where applicable. |
| Review state | Extracted items carry `review_status`: `unconfirmed`, `confirmed`, `corrected`, `rejected`. |
| History | Clinical records are never overwritten in place: material changes create a history row (Sections 5.2, 5.4). |
| Deletion | `deleted_at` (soft delete) where retention or audit rules apply; hard delete after the retention period. |
| Sensitive data | Secrets (password hashes, token hashes) only in auth tables. Audit rows never hold medical content, passwords, or tokens. |
| Units | Original value and unit are always kept; normalised values are stored alongside, never instead. |

### 2.1 Clinical Dates

Clinical dates (`observed_at`, `document_date`, etc.) are paired with a `*_precision` field (`day`, `month`, `year`, `unknown`) so an approximate date is never presented as exact.

## 3. Relationship Overview

```
users ─┬─< refresh_tokens
       ├─< password_reset_tokens
       ├─< email_deliveries
       ├─< audit_events (user_id nullable)
       ├─< profile_values ─< profile_value_history
       ├─< conditions
       ├─< documents ─┬─< processing_jobs
       │              ├─< observations ─< observation_corrections
       │              └─< suggestions
       ├─< medications ─< medication_history
       ├─< follow_ups
       ├─< alerts >── safety_rules
       ├─< ai_summaries
       ├─< exports
       └─< deletion_requests
```

`─<` = one-to-many. Records that come from a document also reference `documents.id` (`source_document_id`).

## 5. Health Record Entities

### 5.1 documents
| Field | Notes |
|---|---|
| id, user_id | |
| storage_key | Opaque key `{user_id}/{document_id}` in document storage; never a public URL. Null on a tombstone. |
| title | The user's name for the document (required by the API, 1–200 characters). Null on a tombstone. |
| original_filename | Sanitised name of the uploaded file, used for downloads. Null on a tombstone. |
| media_type | `application/pdf`, `image/jpeg`, `image/png` |
| size_bytes | ≤ `MAX_UPLOAD_MB` |
| sha256 | Duplicate detection: unique per user **among non-deleted rows** (partial unique index), so a deleted file can be uploaded again. Null on a tombstone. |
| category | `lab_report`, `prescription`, `discharge_summary`, `consultation_note`, `imaging_report`, `other`, `unknown` |
| provider_name | Nullable (hospital, lab, clinic, clinician) |
| document_date, document_date_precision | |
| processing_status | Job lifecycle (Section 5.2). New uploads start as `pending`. |
| search_vector | `tsvector` over category, provider, and extracted text (added with the search feature) |
| created_at, updated_at, deleted_at | |

**Tombstone:** deleting a document removes the stored file and clears `storage_key`, `title`, `original_filename`, `sha256`, `provider_name`, and `document_date`. The row keeps only `id`, `user_id`, `media_type`, `size_bytes`, `category`, timestamps, and `deleted_at` for audit integrity, and it is excluded from every query.

### 5.4 profile_values and conditions
**profile_values:** `id`, `user_id`, `field` (`date_of_birth`, `sex`, `blood_group`, `allergy`, `height`, `weight`, …), `value`, `unit`, `origin`, `suggestion_id` (nullable), `created_at`, `updated_at`, `deleted_at`. Multi-valued fields (allergies) use one row per value.
**profile_value_history:** `id`, `profile_value_id`, `previous_value`, `changed_at`, `change_origin`.
**conditions:** `id`, `user_id`, `name`, `status` (`active`, `resolved`, `unknown`), `onset_date`, `onset_precision`, `origin`, `source_document_id`, `review_status`, `search_vector`, timestamps.

### 5.5 medications
| Field | Notes |
|---|---|
| id, user_id | |
| name, strength, dosage_text, frequency_text, route | As documented or entered |
| start_date, end_date (+ precision) | |
| status | `active`, `stopped`, `unknown` (`backend_spec.md` Section 7.3: never inferred active from an old prescription) |
| prescriber_name | Nullable |
| origin, source_document_id, review_status | |
| created_at, updated_at, deleted_at | |

**medication_history:** `id`, `medication_id`, `snapshot` (JSON of previous values), `changed_at`, `change_origin`.

### 5.6 follow_ups
`id`, `user_id`, `title`, `kind` (`checkup`, `investigation`, `appointment`), `due_at`, `timezone`, `recurrence_rule` (nullable RRULE), `status` (`scheduled`, `completed`, `cancelled`), `completed_at`, `origin`, `suggestion_id`, `source_document_id`, timestamps. "Overdue" is computed (`status = scheduled` and `due_at` in the past), not stored.

### 5.7 suggestions
As `backend_spec.md` Section 5.3: `id`, `user_id`, `suggestion_type` (`profile_value`, `follow_up`), `target_field`, `suggested_value`, `unit`, `original_text`, `source_document_id`, `source_location`, `confidence`, `validation_findings`, `status` (`pending`, `accepted`, `corrected`, `rejected`, `superseded`), `reviewed_at`, `corrected_value`, `result_entity_id`, `processing_job_id`, `created_at`.

### 5.8 safety_rules and alerts
**safety_rules:** `id`, `code`, `version`, `description`, `criteria` (JSON, deterministic), `severity` (`info`, `warning`, `urgent`), `source_reference` (validated source), `approved_by`, `approved_at`, `active`. Unique (`code`, `version`). Rules are global, not user-owned, and change only through controlled change management.
**alerts:** `id`, `user_id`, `rule_id`, `rule_version`, `severity`, `status` (`open`, `acknowledged`, `resolved`), `input_refs` (JSON list of observation/document IDs), `explanation_text` (AI, labelled), `next_steps`, `acknowledged_at`, `resolved_at`, `created_at`.

### 5.9 ai_summaries
`id`, `user_id`, `scope` (`document`, `history`), `content`, `source_refs` (JSON), `general_knowledge_sections` (JSON flags, `DL_AI_spec.md` Section 6.1), `model_version`, `prompt_version`, `created_at`.

### 5.10 exports and deletion_requests
**exports:** `id`, `user_id`, `format` (`pdf_summary`, `csv`, `json`), `status` (job lifecycle), `storage_key`, `expires_at`, `created_at`.
**deletion_requests:** `id`, `user_id`, `scope` (`record`, `document`, `account`), `target_id`, `status` (`requested`, `completed`, `failed`), `requested_at`, `completed_at`.

## 6. Search

PostgreSQL full-text search (`backend_spec.md` Section 7.1): `search_vector` columns on `documents`, `observations`, and `conditions`, with GIN indexes. Every search query filters by `user_id` first. Search text is never logged.

## 7. Integrity Rules

- Foreign keys use `ON DELETE RESTRICT` for clinical data (deletion goes through `deletion_requests`), and `CASCADE` only for auth tokens of a deleted user.
- `(user_id, sha256)` unique on non-deleted `documents` rows; `idempotency_key` unique on `processing_jobs`.
- State transitions (jobs, suggestions, follow-ups, alerts) are validated in services; invalid transitions are rejected.

## 8. Change Management

Schema changes are made through Alembic migrations (`backend_spec.md` Section 11.1) and must update this document in the same change.
